# 팬아트 제한 대기·자동 복구·최종 결과 알림

## 목적 / 완료 조건
2026-10-10 `upstream_backoff_active` 사례를 재현하고, 원본 401/403/429 보호를 해제하지 않은 상태에서 당일 자동 복구를 연결한다. 기존 정상 스냅샷, 다른 일정/영상/쇼츠/노래책 배치와 사용자 데이터는 변경하지 않는다.

## 정책
- 기존 01:00 KST 본 배치를 유지한다. 401/403/429 후 6시간은 원본 수집을 하지 않는다.
- `status=1`은 읽기 전용이며 `retry.version=2`, 한국 날짜, 실제 시도 횟수, `state`, `backoffUntil`, `nextAttemptAt`을 제공한다.
- 대기는 `deferred`로 기록하고 실제 수집 이력에 넣지 않는다. 과거 `upstream_backoff_active` 기록도 실제 시도에서 제외한다.
- 실제 수집은 하루 총 4회, 실패 후 최소 30분 간격이다. 접근 제한이면 더 긴 6시간을 적용한다. 성공 후 당일 재수집하지 않는다.
- 제한 만료는 메타데이터/이미지 제한 캐시 중 늦은 시각으로 판정한다. 실제 수집에서 확인한 제한은 릴리스 밖 일배치 저장소에도 보존한다.
- 중단된 running 기록은 120초 이후 최소 재시도 간격을 적용해 회복한다. 파일 잠금과 기존 원자적 이미지 저장/검증은 유지한다.
- KST 23:50 이후 신규 수집을 시작하지 않는다. KST 다음 날 01:00부터 새 일자의 시도 예산을 적용한다. 6시간 제한이 날짜를 넘으면 계속 존중한다.

## 운영 예약 (KST)
| 작업 | 시각 | 역할 |
|---|---|---|
| 기존 팬아트 백업 | 01:00 | 고정 원본 수집 |
| 기존 이름의 팬아트 보고 | 01:05 | 새 `fanart-daily-recovery` 함수의 initial 모드 |
| `fanart-daily-recovery-kst` | 01~23시 매시 20/50분 | 상태만 확인하고 ready일 때만 고정 배치 호출 |
| `fanart-daily-final-report-kst` | 23:55 | 미완료 작업의 당일 최종 실패 보고 |

01:05에는 성공 또는 대기/실제 수집 오류와 재시도 가능 시각을 구분한다. 이후 성공하면 최종 성공, 실제 시도 4회 소진이면 최종 실패, 계속 제한 상태면 23:55에 최종 실패를 보낸다. 최초 성공을 이미 보고한 날에는 같은 성공을 다시 보내지 않는다. 최초 호출 누락은 다음 정기 점검에서 보완한다. 다른 배치의 통합 보고는 기존 함수를 유지한다.

## 저장 / 보안
- `fanart_recovery_state`: 날짜별 최신 점검, 대기 시각, 실제 시도와 저장본 상태.
- `fanart_recovery_notifications`: 날짜+initial/final 유일 키, 원자적 전송 선점, Discord 전송 결과/메시지 ID. RLS 활성, anon/authenticated/PUBLIC 권한 없음, service_role만 읽기/쓰기.
- 기존 DB의 monitor_token과 Discord Webhook을 서버에서만 재사용한다. 새 함수는 POST + 전용 헤더 인증. URL/날짜/force 입력을 허용하지 않는다. service key와 webhook은 응답/로그/저장소에 포함하지 않는다.
- 전송이 명시적으로 거부된 경우 최대 3회, 최소 30분 간격 재시도. 네트워크 시간 초과/5xx는 전달 여부가 불명확하므로 unknown으로 남기고 맹목적으로 재전송하지 않는다. sending이 장기간 남으면 운영 점검이 필요하다. 외부 HTTP와 DB 사이의 엄밀한 exactly-once를 보장한다고 주장하지 않는다.
- 기존 initial 알림이 이미 발송된 배포 당일에는 원장을 이관하여 중복 발송을 막는다.

## 검증 / 배포 순서
1. PHP 제한/시도/날짜/중단 복구 오프라인 테스트, Node 판정/메시지 테스트.
2. 기존 PHP 이미지 스냅샷·배포/브라우저 회귀, `npm run verify`, `npm run check:backend`, Deno 타입 검사, 격리 PostgreSQL RLS/중복 선점 검사.
3. develop → main PR의 필수 검사와 관련 회귀를 통과한 뒤 기존 GitHub Actions로 PHP 배포.
4. `supabase/ops/fanart_recovery.sql` 적용, 검증된 Edge 함수 배포(`verify_jwt=false`, 본문 전용 토큰 인증), 인증 거부와 dry-run 확인.
5. 상태 API 버전2 및 정상 저장 이미지 확인 후 `fanart_recovery_cron.sql`로 팬아트 예약만 연결한다. cron 호출 성공과 실제 업무 결과는 별도로 확인한다.

## 되돌리기
추가된 recovery/final 예약만 비활성화하고 기존 fanart 보고 예약의 대상 함수를 daily-batch-report(mode=fanart)로 복원한다. PHP는 기존 원자적 릴리스 롤백 경로를 사용한다. `_fanart_daily`와 알림/점검 기록은 삭제하지 않는다. 과거 버전 상태 API에는 새 복구 함수가 원본 재시도를 하지 않는다.

## 확인 범위
미래 원본 접근 제한을 운영에서 강제로 만들지 않는다. 대기→복구/실패는 격리 테스트로 검증하고, 배포 당일 실제 상태와 예약을 별도로 확인한다. 네이버가 지속적으로 원본 접근을 거부하면 자동 재시도가 있어도 새 백업 성공은 보장되지 않는다.
