# 노래책 삭제·복원

## 확인 및 범위
기존 SongbookV2Page/SongEditor/songbookStore에는 노래 삭제 버튼·저장 함수가 없으며, songbook_entries의 DELETE 권한도 제공하지 않는다. 자동 수집 ‘제외’는 가창 기록 한 건에 대한 검토 결정이고 노래 자체 삭제와 다르다.

곡 상세에 관리자 전용 ‘노래 삭제’ → 곡명·가수 확인 → ‘삭제하기’를 추가한다. 성공한 뒤에만 목록·검색·건수·현재 브라우저 즐겨찾기와 CSV에서 제외하고 상단 알림을 표시한다. 실패 시 확인 창과 곡을 유지한다. 검색 조건을 지우지 않고 마지막 페이지를 보정한다. 툴바 아래 ‘삭제한 노래’에서 복원할 수 있다.

## 저장 설계
기본 정적 목록+수동 수정+자동 곡이 합쳐지는 구조이므로 수동 DB 행만 DELETE하면 기본곡이 다시 나타날 수 있다. 별도의 songbook_deletions 표식으로 논리 삭제한다. 원곡 정보·난이도·숙련도·가창 검토 결정은 보관한다. 공개 ID 조회와 서버 SELECT 정책에서 일관되게 제외하고, 자동 수집은 원래 식별자를 계속 인식하므로 같은 ID가 정기 수집으로 되살아나지 않는다. 이미 삭제한 곡의 새 가창 승인은 서버에서 거부한다. 복원 시 보관된 데이터가 다시 보인다. 원본 YouTube/SOOP 영상 자체는 삭제하지 않는다. 삭제는 데이터 완전 파기가 아니라 노래책 비노출이며, 기존 배포 번들 및 외부 영상은 남는다.

삭제·복원·삭제 목록 RPC는 명시적으로 기존 admins/auth.uid()를 확인하고 authenticated에만 실행을 허용한다. 공개에는 song_id만 제공하며 삭제자·제목 스냅샷은 직접 조회할 수 없다. 제한된 SECURITY DEFINER 함수는 고정 search_path와 스키마 한정 이름을 사용한다. 삭제 시 수동 편집 revision을 대조하고 복원은 해당 삭제 건의 토큰을 대조한다. 새 권한이나 계정을 부여하지 않는다.

## 검증·배포
기존 포함 Node·빌드·백엔드 문법 검사와 실제 운영모드 앱의 모의 인증/API 브라우저 검증, 격리 PostgreSQL의 삭제·복원·공개 조회/쓰기 제한·자동 재생성 방지 검증을 수행한다. CI 통과 후 additive migration 적용, develop→main PR 및 기존 Actions 배포와 읽기 전용 운영 검사로 마무리한다. 실제 사용자 곡은 테스트 목적으로 삭제하지 않는다. 자동 수집/Discord/배치 스케줄·API 키는 변경하지 않는다.

로컬 작업은 기존 첨부 소스 스냅샷에서 시작했으며, 실제 변경 파일의 blob과 최신 브랜치를 대조한다. 최종 통합 검사는 최신 develop 기준 GitHub Actions가 실행한다. 완료 SHA와 실행 결과는 PR에 기록한다.

## 승인 후 재개와 503 검사
사용자가 삭제·복원용 운영 테이블/함수 및 관련 조회 정책 변경과 운영 배포를 명시적으로 승인한 뒤 재개했다. 적용 전 객체 존재 여부를 확인하며, 이미 적용된 migration을 반복 실행하지 않는다. migration 자체는 기존 곡이나 가창 기록을 삭제하지 않고 빈 삭제 상태 테이블과 제어 기능을 추가한다.

직전 브라우저 검사의 503 오류 안내 실패 원인은 supabase-js 2.116.0의 기본 GET 재시도(1초→2초→4초)보다 짧은 5초 assertion 대기였다. 제품의 재시도나 오류 처리를 없애지 않는다. 재시도 중 기본곡이 노출되지 않는지, 실제 재시도가 발생하는지, 15초 이내 오류 안내가 나오는지, ‘다시 불러오기’로 복구한 뒤에도 삭제 상태가 유지되는지를 검증한다. 이 대기값은 유한한 테스트 관측 시간이며 운영 통신의 15초 제한을 새로 구현했다는 뜻은 아니다.

공식 재시도 동작: https://supabase.com/changelog/45071-automatic-postgrest-retries-for-transient-errors
