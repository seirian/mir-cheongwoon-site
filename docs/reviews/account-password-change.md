# 내 정보 — 비밀번호 변경

## 화면과 동작
로그인한 `/account` 내 정보에 비밀번호 변경 버튼을 추가한다. 별도 화면 주소는 `/account?mode=password`이며 기존 비밀번호·새 비밀번호·새 비밀번호 다시 입력 세 칸이다. 새 비밀번호는 기존 가입 정책과 같은 8~128자로 제한하고 확인값 일치·기존 비밀번호와의 차이를 검사한다. 비밀번호 공백은 임의로 제거하지 않는다. 오류별 안내, 중복 제출 방지, 취소/성공 시 입력 초기화, 완료 후 재로그인을 제공한다.

기존 query mode를 사용하므로 Apache 경로·정적 메타데이터·공유 이미지·홈 CSS를 바꾸지 않는다. 계정 noindex를 유지하며 익명 접근은 로그인만 표시한다. 이메일 복구 경로도 유지한다.

## 최종 인증 구조
추가 Edge Function 배포 요청이 도구 안전 검사에서 차단되어 해당 배포는 중단했다. 다른 경로로 우회 배포하지 않는다. 신규 서버 파일은 브랜치에서 제거했다. 최종 구현은 이미 사용 중인 Supabase Auth의 공식 클라이언트 API만 호출하며, 비밀번호가 별도의 애플리케이션 서버나 함수로 전송되지 않는다.

1. 기존 클라이언트 `auth.getUser()`로 로그인 사용자를 실제 Auth 서버에서 확인한다.
2. 별도 메모리 전용 클라이언트로 그 사용자의 확인된 이메일과 기존 비밀번호를 `signInWithPassword()`에 전달한다. 실패 시 비밀번호 업데이트를 호출하지 않는다.
3. 재인증 결과의 사용자 ID와 기존 로그인 ID를 비교하고, 도중 계정 전환/로그아웃이 없었는지 다시 확인한다.
4. 재인증된 클라이언트에서만 `updateUser({password, current_password})`를 실행한다. 기존 세션에 새 세션을 덮어쓰거나 관리자 비밀번호 강제 변경 API를 쓰지 않는다.
5. 성공 시 세션 종료를 요청하고 입력을 비워 로그인 화면을 표시한다. 임시 클라이언트는 모든 종료 경로에서 정리한다. 종료 통신 실패로 이미 변경된 비밀번호를 실패로 알리지 않는다.

임시 클라이언트는 persistSession=false, autoRefreshToken=false, detectSessionInUrl=false 및 고유 storageKey로 생성한다. 비밀번호·임시 토큰을 URL/로그/브라우저 저장소/DB에 기록하지 않는다. Supabase Auth의 기존 비밀번호 보안 및 호출 제한은 그대로 적용된다. MFA 설정 계정은 비밀번호만으로 추가 인증을 우회하지 않는다. DB/RLS/Storage/기존 member-auth 함수/프로젝트 인증 정책을 변경하지 않는다. 이 화면의 검증 흐름을 구현하는 것으로, 프로젝트의 모든 직접 Auth API 호출에 새로운 전역 정책을 강제하는 변경은 아니다.

## 검증
새 18개 Node 단위 테스트: 입력 불일치·기존 비밀번호 오류·검증된 계정 일치·세션 만료/계정 전환·서비스 오류·정리 실패·중복 업데이트 방지·문자열 원형 유지. 운영 계정이나 네트워크를 사용하지 않는다.
브라우저 테스트: 실제 빌드와 격리된 Native Auth 응답으로 1440/390px의 내 정보 진입·세 입력·오류·취소·새로고침·중복 제출·성공/로그아웃·임시 토큰 비저장·익명 접근·기존 복구 보호를 검증한다. 운영 검사는 익명 읽기 전용이며 실제 회원 비밀번호는 임의 변경하지 않는다.
